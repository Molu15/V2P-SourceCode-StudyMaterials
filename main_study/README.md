# Main Study Scripts

Simulation and communication scripts used to run the main study (N=30, within-subject,
Adaptive System vs. Fixed Baseline).

## Contents

| File | Purpose |
|---|---|
| `run_sim.py` | Runs the CARLA driving scenario logic: vehicle spawning, scenario sequencing, trial triggering (Target/Catch/Safe), TTC-based warning state machine, and CSV logging. Also launches `main_bridge.py` automatically as a subprocess. |
| `main_bridge.py` | UDP relay + sensor-fusion layer between the phone, the host laptop, and CARLA: forwards phone sensor data (yaw, accelerometer) to CARLA for pedestrian tracking, and relays alarm commands from CARLA back to the phone |

## Requirements

- CARLA 0.9.15 (Python API)
- Python 3.10.11
- Python packages: `pygame`, `keyboard`, `numpy` (see `run_sim.py` imports)
- `main_bridge.py` uses only the standard library (`socket`, `json`, `threading`)

## Network architecture

`main_bridge.py` sits between the phone, CARLA, and the simulation host, using five separate
UDP ports:

| Port | Direction | Purpose |
|---|---|---|
| 5006 | Phone → Bridge | Phone sensor data (yaw, accelerometer) |
| 5007 | Bridge → Phone | Alarm commands (Flutter-side receiver) |
| 5008 | Bridge → Phone | Alarm commands (native Kotlin overlay service — see `smombie_bridge/UdpOverlayService.kt`) |
| 5010 | Bridge → CARLA | Forwarded/smoothed sensor data for pedestrian dead-reckoning |
| 5011 | CARLA → Bridge | Alarm trigger commands generated by `run_sim.py`'s warning state machine |

Alarm commands are sent to **both** 5007 and 5008 redundantly (Flutter and native Kotlin
receivers on the phone side).

`main_bridge.py` also performs on-the-fly **dead-reckoning distance calibration**: at the start
of a session, the participant walks a known calibration distance so the bridge can convert
detected steps (from phone accelerometer data) into meters from the curb.

## Study design summary

- N=30 participants, within-subject design
- Two counterbalanced blocks: Adaptive System vs. Fixed Baseline
- 9 trials per block (5 Target, 2 Catch, 2 Safe)
- Counterbalancing: odd participant IDs = Adaptive first, even PIDs = Baseline first
- Two-stage warning escalation, driven by time-to-collision (TTC) thresholds in `run_sim.py`:
  - **Early warning ("f" alarm)** at TTC = 5.0 s (adaptive condition only)
  - **Full multimodal alert ("vha")** at TTC = 2.5 s (both conditions)
  - A `MIN_TOTAL_TTC` floor introduces a systematic, logged `TimingError`

## Usage

Start the CARLA server first, then run:

```bash
python run_sim.py
```

This automatically launches `main_bridge.py` in a separate console window. You'll then be
prompted for:

1. **Participant number** (integer) — determines counterbalancing order automatically
   (even → Baseline first, odd → Adaptive first)
2. Per-block **run order** — press Enter to follow the suggested trial sequence, or type a
   specific run/scenario ID

Logs are written to `logs/P<participant_number>/`, including `run_order.csv`.

An optional `pedestrian_config.json` (same folder as `run_sim.py`) can override the default
floor-marker distances (`DIST_A_TO_B`, `DIST_B_TO_DANGER`) for a given physical setup.
